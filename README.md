# Avito DS Bootcamp - кандидатогенерация

Задача: по запросу отобрать из корпуса (~189к объявлений) до 50 кандидатов, чтобы туда попали объявления, которые юзер реально выбрал. Метрика Recall@50

Финальный скор на лидерборде: **0.82**

Саму README'шку частично генерил

## Как шёл по решению

1. Сначала покопался в данных. Категория по сути ничего не даёт (там всё услуги), доставки нет, а вот география влияет сильно.
2. Сделал бейзлайн чисто на семантике (эмбеддинги e5-base, косинус) + гео-фильтр. Получил 0.75.
3. Дальше бустинг поверх кандидатов, чтобы заюзать остальные данные: расстояние, рейтинг, отзывы, цену, флаги. Стало 0.80.
4. Пересчитал эмбеддинги на модели посильнее (e5-large) и добавил фичи по истории "запрос -> микрокатегория". Итог 0.82.

## Что где лежит

- `Avito_DS_Bootcamp.ipynb` - EDA, гео-фильтр, эмбеддинги e5-base, сплит на валидацию и бейзлайн
- `Avito_boosting_binary.ipynb` - финальное решение, из него получается итоговый answer.csv

## Запуск

Всё запускал в Google Colab, данные и эмбеддинги лежат на гугл диске.

Эмбеддинги e5-large считаются долго (~40 мин на GPU), так что проще взять мои:

1. Вот папка: https://drive.google.com/drive/folders/11LUqDu9dz0BatdOWVN5YCZiVFtmoj_d2?usp=sharing
2. Скопировать её (или добавить ярлык) в корень "Мой диск" с именем `avito_bootcamp`. Должно получиться так:

```
MyDrive/avito_bootcamp/
├── datasets/        # три parquet'а из задания
├── emb_e5_base/     # эмбеддинги e5-base + val_groups.parquet
├── emb_e5_large/    # эмбеддинги e5-large + val_groups.parquet
└── boosting/        # модель и финальный answer_boosting.csv
```

3. Открыть `Avito_boosting_binary.ipynb` в колабе и прогнать все ячейки. GPU не нужен, на CPU минут 20-30.
4. В конце печатается MD5 ответа, должен совпасть с тем, что лежит в `boosting/answer_boosting.csv`: `c34aa37bace57ca886bd68fff0cd8683`

Если папки лежат в другом месте - поменять `DATA_DIR`, `EMB_DIR`, `OUT_DIR` в первой ячейке.

По воспроизводимости: сиды зафиксированы, у LightGBM стоит `deterministic=True`, сплит валидации сохранён в `val_groups.parquet`. Финальный ответ я получал на CPU. На GPU поиск идёт в fp16 и порядок при одинаковых косинусах может чуть поплыть, так что для точного совпадения файла лучше тоже CPU.

## Данные и фичи

Что увидел в EDA:
- `search_category` - в бенче всего 0 и 114, по текстам всё услуги. Фильтровать по категории не стал. Объявления не из 114 (~1% корпуса) тоже оставил, там бывают ответы на запросы с категорией 0.
- доставка - 12 строк на весь train и 0 в бенче, выкинул из головы.
- локация - 83% выборов из той же `location_id`, остальные в основном из соседних городов (медиана ~16 км). Но у 17% запросов бенча в корпусе вообще нет объявлений с их `location_id` (это области/регионы). Поэтому фильтр сделал не по id, а по расстоянию между центрами локаций.
- train и корпус почти не пересекаются: только 6.6% выборов train про объявления из корпуса, и только 37% текстов запросов бенча встречаются в train. Запоминать "запрос -> объявление" смысла мало, нужна семантика.

Гео-фильтр: для каждой локации поиска беру все локации объявлений в радиусе 40 км. Это покрывает 96% выборов в train, пул по медиане ~3.5к объявлений. Есть локация 621540, которая ведёт себя как "вся Россия" (медиана расстояния до выборов 640 км) - её ловлю правилом (медиана > 300 км) и гео для неё не применяю.

Тексты для эмбеддингов:
- запрос = текст + фильтры поиска (с фильтрами было на ~2.5 п.п. лучше, чем без)
- объявление = заголовок + параметры + первые 500 символов описания

Фичи для бустинга (одна строка = запрос + кандидат):
- сходство: косинус (с фильтрами и без), ранг кандидата внутри запроса, отставание от топ-1. Относительные фичи нужны, потому что у разных запросов косинус в разном масштабе
- гео: расстояние, в гео-пуле или нет, та же локация или нет, флаг "вся Россия"
- объявление: рейтинг (0 и пусто -> NaN), сглаженный рейтинг (чтобы 5.0 по 1 отзыву не был лучше 4.9 по 300), log отзывов, цена (1 руб = договорная -> NaN + флаг), цена относительно медианы по микрокатегории, скрытый телефон, запрет сообщений
- история: доля выборов микрокатегории кандидата по этому тексту запроса в train, сколько всего было таких выборов, и доля микрокатегории среди топ-20 по косинусу (эта работает и для новых запросов)

Больше всего по gain дают расстояние, ранг по косинусу, косинус без фильтров, доля микрокатегории в топ-20 и совпадение локации.

## Модели

- Кандидаты: `intfloat/multilingual-e5-large` (в бейзлайне `multilingual-e5-base`), поиск по косинусу. На запрос беру топ-100 внутри гео-пула + топ-50 без гео, выходит ~145 кандидатов.
- Ранжирование: LightGBM, бинарка "выберут / не выберут", в ответ идёт топ-50 по вероятности. Негативы - невыбранные кандидаты того же запроса. Вес позитива = 1 / кол-во правильных ответов у запроса, чтобы было как в метрике. Учил на 10к запросов train, early stopping на отдельной 1к.
- В ответе 47 мест из гео-пула и 3 лучших из остальных - под удалённые услуги.

Пробовал ещё lambdarank (LGBMRanker), но на CPU он учился очень долго, а порядок внутри топ-50 на метрику не влияет, так что остался на бинарке.

Из open-source: sentence-transformers, модели intfloat/multilingual-e5-base и e5-large с Hugging Face, lightgbm, torch, pandas, numpy. Всё локально, без внешних API.

## Как проверял качество

- В train нет query_id, поэтому запрос = группа строк с одинаковыми `search_*`. У 85% таких групп один ответ, у 9.5% два - совпадает с тем, что сказано в условии.
- Валидация - 2500 групп, но не рандомных: подобрал так, чтобы "знакомых" текстов (которые есть в остальном train) было 37%, как в бенче. Если брать рандомно, их было бы 87%, и валидация была бы слишком лёгкой.
- Корпус для валидации = корпус бенча + правильные ответы валидации (иначе их там просто нет).
- Всю статистику по истории считаю без валидации, модель учится на других запросах.
- Первый сабмит использовал, чтобы понять, насколько можно верить валидации: там было 0.805, на лидерборде 0.75. Валидация чуть оптимистичнее, но изменения в одну сторону, так что дальше сравнивал варианты на ней.
- Модель и бейзлайн сравнивал на одних и тех же кандидатах: потолок кандидатов 0.886, чистый косинус 0.818, модель 0.857.
- Перед каждой отправкой гонял проверку формата (колонки, все query_id на месте, не больше 50 id, без повторов, все id из корпуса).

## Какие косяки нашёл и что с ними сделал

- Фильтр по совпадению `location_id` терял 17% выборов, а 17% запросов бенча вообще оставались без своих объявлений -> перешёл на расстояние между центрами локаций.
- "Вся Россия" (621540) - центр такой локации ни о чём -> правилом отключаю для неё гео-фильтр.
- Удалённые услуги (обзвон, дизайн, юристы и т.п.) выбирают за сотни км -> 3 места из 50 отдаю кандидатам без гео-фильтра, это дало +0.3 п.п.
- 63% запросов бенча новые, истории по ним нет -> основной сигнал всё равно семантика, плюс фича "доля микрокатегории в топ-20", которой история не нужна. На новых текстах модель даёт +4 п.п. к косинусу, на знакомых +3.4.
- Утечка в фичах истории: для запросов из трейна бустинга в статистике сидел их же ответ -> leave-one-out, вычитаю вклад самого запроса.
- Запросы с сотнями ответов (маникюр в Москве) перетягивали обучение -> веса 1 / кол-во ответов.
- Позитивы подмешаны в корпус из train, и модель могла научиться узнавать "объявление из train" -> ответы одних запросов работают негативами для других.
- Цена 1 руб и рейтинг 0 - это не реальные значения -> в NaN + флаги.
- Координаты и цена лежали строками/Decimal -> привёл к float.
- Пробовал брать больше кандидатов (250 вместо 100) - прироста нет. Значит, упираюсь не в кандидатов, а в фичи. Оставил 100.

Что не добил: по запросам "вся Россия" recall около 0.5, и модель там даже чуть хуже чистого косинуса - без гео среди похожих объявлений угадать нужное сложно. Таких запросов в бенче ~4%
